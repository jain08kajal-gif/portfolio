Loco Viewer App: Web, Mobile Web, App

Scaling a design system across a 6-person team in one month

Company

Loco

Surfaces

App, Web, Mobile web

Timeline

1 month

Team

5–6 designers

Visit Loco →

Context

Loco needed a full visual overhaul of its viewer experience across three surfaces (app, web, and mweb) in one month. The scope was explicitly visual and structural, not a UX redesign: existing flows and interaction patterns stayed as they were, re-skinned using competitor visual language (Twitch) as a reference point, since neither design nor engineering had the bandwidth for original UX exploration in that timeframe. A team of 5-6 designers worked on this in parallel.

Constraint

  • One month, three surfaces: an aggressive timeline for a full visual system, not just a feature.
  • No new UX decisions in scope; devs couldn't ship structurally new features that fast, so the redesign had to work within existing flows.
  • Branding wasn't finalized: colors, gradients, and iconography were still coming from an external agency, expected weeks into the project.
  • 5-6 designers working simultaneously meant consistency wasn't guaranteed by default. Nothing enforced shared component usage across the team.

Decision

I owned design and system consistency for a set of core flows (Homepage, Livestream, Fullscreen Livestream, and Leaderboard), translating reference screens into Loco's visual language while building them from shared, reusable components rather than one-off screens.

A team-level decision I applied and maintained across my flows: rather than hardcoding colors and styles into components, we introduced semantic tokens, driven by a dev need for simpler dark/light mode switching. On high-traffic surfaces like Homepage and Livestream, that meant every component had to reference tokens consistently, not just look right in one theme.

Keeping six designers aligned against the same reference source took constant coordination. Without it, interpretation naturally drifted.

Trade-off

  • Speed and dev-need-driven architecture took priority over original UX exploration. The goal was a cohesive, systemized visual layer, not new interaction design.
  • Distributed execution across 6 designers meant some inconsistency was unavoidable: not everyone used components as intended, and reconciling that came later rather than being prevented upfront.

Outcome

  • When branding was finalized roughly three weeks in, the semantic token structure (originally built to solve theme-switching) meant the whole system's colors, gradients, and iconography were updated in a single night, rather than requiring screen-by-screen rework across all three surfaces. This wasn't the original intent of the token system, but a direct payoff of building it correctly.
  • The design system built in this sprint is still used today to create new flows on the platform. That's a stronger, longer-lasting outcome than a one-time launch.
  • Post-branding, a sanity pass and reconciliation of inconsistent component usage was still required, which fed into tighter guidelines for adoption going forward.

Reflection

Even with a solid token architecture, inconsistency persisted where designers bypassed shared components. That's a reminder that a system is only as strong as its adoption discipline. Given the time constraint, we couldn't fully solve for governance in the moment; next time, I'd push for lighter-weight enforcement (e.g., a shared component checklist before merging designs) built into the parallel workflow from day one, rather than reconciling inconsistency after the fact.
